High

CR-01 — No re-injection guard in init()

Checklist #2 — check before injecting

init() unconditionally overwrites #site-main and rebuilds the whole section every time it runs, with no check for whether the redesign markup is already there.

// vB.js:760-768
function init() {
  document.body.classList.add(variation_name);
  var mountEl = document.querySelector(MOUNT_SELECTOR);
  if (!mountEl) return;
  var controlJoinAnchor = findControlJoinAnchor(mountEl);
  mountEl.innerHTML = buildPageHTML();   // <-- no existence check first

Why it matters: if the variation script executes twice on the same page load (SPA-style re-injection by the test platform, a duplicated script tag, back/forward-cache restore), the section is rebuilt from scratch and every listener below gets re-attached on top of the old ones — root cause for CR-02.

High

CR-02 — Listeners not gated behind a one-time-init flag

Checklist #4 — event handlers under a single window-flag guard

None of the following are deduplicated against repeat calls:

  • document.addEventListener("click", ...) — vB.js:724 (closes open tooltip on outside click)
  • window.addEventListener("scroll", ..., true) — vB.js:734-740
  • window.addEventListener("resize", ...) — vB.js:731-733 (tooltip) and vB.js:611-612 (Swiper refresh)
  • wireSmoothScrollLinks() — vB.js:630, attaches a fresh click listener per a[href^="#"] with no dedupe

Why it matters: combined with CR-01, a second init() run means two independent activeWrap closures both listening for outside clicks — tooltip open/close state can desync between them, and smooth-scroll links fire scrollIntoView twice per click. Standard fix pattern: if (window.__creT21Inited) return; window.__creT21Inited = true; before wiring anything.

High

CR-03 — No fallback if the Swiper CDN fetch fails

Checklist #5 — fallback when the code doesn't work properly
// vB.js:776-780
injectScripts()
  .then(() => {
    initSwiper();
  })
  // <-- no .catch()

Why it matters: if the fetch to cdnjs.cloudflare.com/.../swiper-bundle.min.js fails (ad-blocker, CSP, network blip), the rejection is swallowed silently — it's async, so the outer try/catch around the whole IIFE (vB.js:788) never sees it. Result: initSwiper() never runs, and the 4 testimonial slides render as an unstyled stack with dead nav buttons and no pagination — with no fallback layout in vB.css for the no-JS-carousel case.

Medium

CR-04 — Scroll/resize handlers are not debounced

Checklist #6 — observer/scroll detector should debounce
// vB.js:734-740
window.addEventListener(
  "scroll",
  function () {
    if (activeWrap) positionTooltip(activeWrap);
  },
  true
);

Why it matters: positionTooltip() calls getBoundingClientRect() twice and writes 3 inline styles on every scroll tick with no throttle — layout thrashing during fast scroll, most visible on lower-end devices. The resize handlers (vB.js:612, 731-733) have the same gap, lower severity since resize fires far less often.

Medium

CR-05 — Swiper bundle re-fetched every page load, never session-cached

Checklist #9 — cache fetched URLs in session storage
// vB.js:28-40
const injectScripts = () => {
  return fetch("https://cdnjs.cloudflare.com/ajax/libs/Swiper/8.3.2/swiper-bundle.min.js")
    .then((res) => res.text())
    .then((code) => {
      new Function(code)();
      ...

Why it matters: this variation re-initializes on every pageview of the AFP membership page, and every single one triggers a fresh fetch + eval of the same ~150KB bundle. Browser HTTP cache may absorb some of this, but there's no explicit sessionStorage cache, so it isn't guaranteed. Should store the fetched text once per session and read it back on subsequent loads instead of re-fetching.

Low

CR-06 — injectScripts() doesn't check if Swiper is already loaded

Checklist #2 — check before injecting (specific case)

injectSwiperCSS() (vB.js:41-42) correctly guards with if (document.querySelector("#cre-swiper-css")) return; before injecting the stylesheet link — but injectScripts() has no equivalent if (typeof window.Swiper === "function") return Promise.resolve(); guard before fetching and re-executing the JS bundle. Same root cause as CR-01/CR-02: harmless on a normal single page load, but wasteful (and potentially double-initializing) on any repeat run.
