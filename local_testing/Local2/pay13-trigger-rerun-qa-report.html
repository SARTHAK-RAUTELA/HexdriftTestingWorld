PAY13 — pay.com.au Modal: Trigger Rerun Against Real Activation Code

QA report — 2026-09-07 (Round 2, same-day rerun of cre-t-13-desktop-trigger-update)

Why this rerun

The client supplied the actual Optimizely Activation Code — the function trigger(activate, options) snippet that decides when to call activate(). This is architecturally separate from the Variation/Control JS (vB.js/v2.js), which only builds and shows the modal. Round 1's fix had guessed at the trigger requirement and baked the 40s-timer/exit-intent logic directly into vB.js/v2.js; this round rebuilds the test around the real two-stage architecture:

pay13-trigger-variation.js / pay13-trigger-control.js   --calls activate()-->   vB.js / v2.js
        (decides WHEN)                                                    (just builds+shows modal)

vB.js/v2.js were stripped back to firing immediately (waitForElement("body", init, 50, 15000)) when activate() calls them.

Control's activation code — derived, not supplied

The client only supplied the variation's activation code (40s timer + exit intent). Per the client's own confirmation — "control fires exit intent only, variation fires exit intent and 40 sec" — pay13-trigger-control.js was derived by removing the 40s-timer block from the variation code, keeping the isMobile guard, cookie, and exit-intent handler byte-identical. If the client later shares the actual control-side snippet, diff it against this derived version before trusting further reruns.

New finding: desktop-only is enforced in JS, not just via the Optimizely audience

Round 1's report stated "there is nothing in the injected code for a device-emulation test to exercise" — true of vB.js/v2.js's content, but the real Activation Code has: 
var isMobile = window.innerWidth < 768;
if (isMobile) { return; }
before setting up either trigger path. This round adds dedicated regression tests confirming the modal never activates on Mobile Chrome (Pixel 5), Mobile Safari (iPhone 12), or a narrow desktop viewport — independent of the Optimizely audience.

Two environment-artifact issues found and fixed in the test fixture (not the client's code)

1. Virtual-clock two-stage timer gap. Once activate() injects vB.js/v2.js, that script registers its own fresh waitForElement("body", init, 50, 15000) poll under the already-installed page.clock fake timer. The test wasn't advancing the clock a second time after activation fired, so init() never ran even though activation itself had succeeded. Fix: added a follow-up page.clock.fastForward(100) after every action that triggers activation.
2. Cookie-on-file://-origin unreliability. The real trigger's fired-flag is a document.cookie write (cre-t-13=modal-triggered; path=/), not sessionStorage like Round 1's hand-built version. Chromium and WebKit silently refuse to persist cookies set on file:// origins (Firefox tolerates it) — an artifact of the fixture's origin, not a defect in the client's code; the modal still displayed and the goal still fired correctly in every case, only the cookie-persistence assertion tripped. Fix: the fixture is now served from a local HTTP server (http://127.0.0.1:<port>/, spun up in test.beforeAll) instead of file://, matching how https://pay.com.au/ actually behaves.
Also added a <meta name="viewport" content="width=device-width, initial-scale=1"> tag to the fixture — without it, mobile/tablet emulated browsers report a stale ~980px layout-viewport width instead of their real device width, making the isMobile check untestable in this environment. Production's real page already has a normal viewport meta tag, so this only mattered for making the fixture trustworthy.

Minor code note (not a bug — harmless by design)

If the 40s timer fires first in the client's real activation code, the mouseout exit-intent listener is never explicitly removed (only the listener's own branch removes it; the timer branch doesn't reach that removal). A later exit-intent event after the timer has already fired still invokes executeActivation("exit_intent"), but the getCookie(...) === "modal-triggered" guard at the top of executeActivation makes it a no-op — confirmed via TC 5, no double-fire occurs. Not worth a client fix, just worth knowing if debugging a "why is this listener still attached" question later.

Not covered by this test suite

This rerun uses a local static fixture (served over HTTP) with the client's activation code + variation/control JS injected directly, per the existing lesson that exit-intent/timer testing against the live pay.com.au page is flaky due to 15+ third-party scripts competing for the main thread. Visual/content assertions (modal layout, copy, CTA behavior) are unchanged from Round 1 — this rerun's scope is specifically the trigger/activation architecture and the newly-discovered desktop-only JS gate.
