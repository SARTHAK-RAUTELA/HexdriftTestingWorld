What this test does

Reorders the 10-partner comparison list and overrides several rating scores/labels, per the ticket's Google Sheet, for two arms. Requirement: with All Pets selected (the default / no filter), the test order + test ratings apply. With any other filter active (Cats, Dogs, breed, ZIP), sorting must revert to the site's native order, but the test ratings must keep showing (not revert to native).

BUG-01 — "Show More" collapse bug (STILL OPEN)

Both vB.js and va3.js intend the list to load fully expanded by default — the code's own comment says so — but the call that would do it, expandIfCollapsed(), is still commented out inside updateFilterState() in the rewritten code. Confirmed on load: only 7 of 10 partner cards are visible and the toggle reads "Show More".

Confirmed live on the real Convert-served page (not just local injection) via direct navigation to both force-preview URLs with zero user interaction: the list is still collapsed to 7/10 cards at ~5 seconds after load — well past the old 3-second re-collapse interval documented in the first pass. The rewrite's own defensive CSS comment ("force all 10 cards visible regardless of the native collapse mechanism") does not hold in practice, because clickNativeButton() still unconditionally does listContainer.classList.add(collapsedClass) on every tick of its polling interval, which overrides that CSS.
New, broader manifestation in the rewrite: the rewrite added eventListeners(), which re-arms the same collapse-fighting polling window on every pet-type tab click (Cats/Dogs/All Pets) and on ZIP change — not just on initial page load. So returning to "All Pets" after any filter, or clearing the ZIP field, now also lands back on the 7-card collapsed state, 100% deterministic across all 7 browsers and both arms.

Impact: every real visitor's first several seconds on the page — and every time they return to "All Pets" from a filter — show only 7 of the intended 10 reordered/re-rated partners. Order and rating values are correct for every card that IS visible in every failure; this is purely a visibility/collapse bug, not a data bug.

Suggested fix: re-enable expandIfCollapsed() in updateFilterState(), and make clickNativeButton()'s classList.add(collapsedClass) conditional (only add if not already expanded by the user) — or stop each polling interval as soon as expansion succeeds. This needs to apply to both the initial init() interval AND the per-tab-click interval added in eventListeners().

BUG-02 — Ratings reverting under filters (CONFIRMED FIXED)

The ticket states: "Whenever any of the filters are active, we will restore the native website behaviour for the sorting order. However, the ratings will continue to be applied from the test."

First pass (2026-09-09): activating Cats, Dogs, or a ZIP code correctly restored native order — but also reverted every rating/score/classification back to native values, because both the order overrides and the rating overrides were gated behind the same body.cre-t-164-default class.
Re-test (2026-09-10): FIXED. The rewritten CSS moves every rating ::after override (.cre-t-135-total, .cre-t-135-classification) out from behind the body.cre-t-164-default gate entirely — only the order/serial-number rules stay gated. Verified live across all 7 browsers, both arms: ratings correctly persist under Cats, Dogs, and ZIP filters, exactly matching the ticket's requirement.

What was verified as correct

  • Order and rating values in both CSS files match the ticket's Google Sheet exactly for every visible card, both arms.
  • Rating overrides exist only where the value actually changes from the current hardcoded page (Embrace/Figo/Odie/AKC intentionally have none).
  • The "duplicate Best Overall" pinned-card architecture works as intended (same pattern as SWF151).
  • Native order-restore under Cats/Dogs/ZIP filters works correctly, and now (post-fix) ratings correctly persist alongside it.
  • Font-size parity holds for every overridden rating (font: inherit).
  • No duplicate-id or console-error regressions in any browser.
  • As of the rewrite, vB.js and va3.js are byte-identical — all arm-specific logic now lives entirely in per-arm CSS.

Methodology

Both arms were tested via local injection of the real vB.js/vB.css and va3.js/va3.css files against the real live site, for consistency across both QA passes (same established pattern as this client's SWF151 suite). Live recon was additionally run directly against both real Convert force-preview URLs to confirm the local-injection results match the real Convert-served experience:

  • V1 (_conv_eforce=100052787.1000257234) — now correctly renders cre-t-164 markup. The previous variation ID (1000257233) rendered as the bare/unmodified page on the first pass, even though the _conv_v bucketing cookie confirmed the session was assigned to it — a Convert wiring gap that has since been resolved by the client.
  • V2 (_conv_eforce=100052787.1000257236) — worked correctly on both passes.
  • BUG-01 was independently reproduced on these real live URLs (not just the local-injection suite) with zero automated interaction, confirming it is not a test-harness artifact.
