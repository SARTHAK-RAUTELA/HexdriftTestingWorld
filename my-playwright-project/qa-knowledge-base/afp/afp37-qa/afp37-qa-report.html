AFP · VWO exp 84 · QA report · 2 Nov 2026

AFP37: Sitewide Login Update Announcement

Variation cre-t-37 (vB.js / vB.css) Browsers Chrome + Safari, desktop + mobile Method Playwright on VWO preview links + manual Chrome pass

Verdict: hold launch until the cookie-banner overlap is fixed

The modal and the eWeb alert match the wireframe in all four browsers: copy, styling, position, the 5-second delay, dismissal, the 7-day cookie, reduced motion and both goals. The blocker is first-time visitors. The modal opens on top of the TrustArc cookie banner, and on phones it covers the "Agree & Proceed" button. The alert also shows on eWeb pages other than login.

Bugs

High

BUG-01 · Modal covers the cookie consent banner for first-time visitors

For anyone who hasn't answered the TrustArc banner yet, the modal opens on top of it. Both use z-index: 999999, and the modal is added later, so it wins. On iPhone 12 and Pixel 5 the card sits directly over the Agree & Proceed button. On desktop it covers the start of the privacy text. The wireframe says the card should stay "clear of cookie notices and other overlays".

Seen in
Chrome, Safari, Mobile Chrome, Mobile Safari (TC-08, 4/4 browsers)
Cause
vB.css already offsets the card by var(--cre-t-37-consent-offset), but vB.js never sets that variable, so the offset is always 0.
Suggested fix
In showModal(), if #truste-consent-track is visible, either wait until it's dismissed before showing, or set --cre-t-37-consent-offset to its height and keep it updated with a ResizeObserver. Waiting is cleaner on mobile, where the banner fills most of the screen.
Medium

BUG-02 · Opens at the same time as other site popups

On the homepage, the site's HubSpot "AFP 2026 · Don't get stuck with FOMO" countdown popup (#hs-web-interactives-top-anchor, with a dark overlay) opens at the same moment, so a first-time visitor sees two popups plus the cookie banner. In the manual Chrome pass, a Hotjar "Quick question" survey (.hj-survey-*, max z-index) also appeared once in the same bottom-left corner, 24px from the edge, over the bottom of the modal. Hotjar is sampled, so this only happens for some visitors.

Seen in
HubSpot popup in all 4 browsers (TC-08b); Hotjar in 1 of about 6 manual loads
Suggested fix
Hold the modal while the HubSpot popup is visible and start the 5s timer after it closes. For Hotjar, move the card up when a survey is present, or ask the client to move the survey to bottom-right. Check with the client first, since the HubSpot popup is their own campaign.
Medium

BUG-03 · eWeb alert shows on non-login pages

The ticket scopes the alert to the eWeb login page. The code adds it above the first #eWebFrameWorkMiddleRow h1 on any eWeb page, with no WebCode check, and the VWO targeting doesn't narrow it either. Verified on Forgot Password (WebCode=ForgotPassword), where it shows above "Forgot your password?".

Seen in
All 4 browsers (TC-21) and the manual Chrome pass
Suggested fix
Gate initAlert() on /WebCode=LoginRequired/i, or add a URL rule in VWO for the eWeb part. It may be wanted on Forgot Password, since that's where people will reset, so confirm with the client before changing.

Lower-priority notes

  • The alert pops in late. On eWeb, VWO adds the alert 2–5s after the page renders, pushing the sign-in form down while someone may already be typing. VWO's "hide modified elements" setting can mask it.
  • Escape only works with focus inside the modal. The keydown listener sits on the modal and focus is never moved into it, so Escape on the page does nothing. The spec doesn't require Escape; the close icon and "Got it" are both keyboard-focusable.
  • The dismiss cookie is host-only (www.financialprofessionals.org). Visitors on the bare domain would see the modal again. Low risk if the bare domain redirects to www.
  • eWeb is already wider than the phone screen. On iPhone 12 the alert is 400px in a 390px viewport (TC-19, marked NOTE), but eWeb renders 411px wide without the variation too, so the alert just follows the existing column. Optional: max-width: calc(100vw - 32px) on mobile.
  • Goals were checked through VWO.event, not network hits. Preview mode doesn't send tracking. Both identifiers (afp37ModalShows, afp37ModalDismissed) match the campaign's goal config.
  • The deployed code matches the local files. The VWO bundle has the same CSS and JS (5s delay, 7-day cookie, eweb.afponline.org branch). Logged-in users weren't tested because there's no test account; the code doesn't branch on login state, so they should see the same thing.
