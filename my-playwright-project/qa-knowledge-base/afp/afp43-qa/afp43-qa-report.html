Bugs

Medium

BUG-01 · Dropdown content stays at the left edge on wide screens

The bar's inner container is centred, so at 1920px its logo starts at x=260. The variation's dropdown panels still put their links at x=44 and the divider at 32–1032px, so the menu reads as detached from the bar above it. At 2560px the gap is 536px. Control at 1920 keeps its links in line with the logo (logo 292 → first link 320). At 1440px and below the two line up, which is why it matches the wireframe there.

Seen in
Chrome and Safari, Program / Hotel / Sponsors (TC-18). Measured at 1920 and 2560px; starts once the viewport is wider than the bar's max-width (~1450px).
Cause
vB.css overrides the panel with a fixed padding: 30px 44px 25px, a fixed grid-template-columns: 524px 1fr and a 1000px divider. That replaces the host's container-relative padding.
Suggested fix
Keep the panel full-bleed, but derive the left padding from the bar container, e.g. padding-left: max(44px, calc((100vw - <bar max-width>) / 2 + 44px)), or keep the host padding and only change the grid. Give the divider the same offset.
Medium

BUG-02 · Desktop visitors under 1200px are bucketed into Variation but see control

vB.js returns early unless (min-width: 1200px) matches, but the VWO audience is "Desktop", which is based on device type, not window width. A 1440×900 laptop at Windows' common 125% scaling has a 1152px CSS viewport. So does any non-maximised window. Those visitors get combination_chosen = 2 and fire the same page and click goals, but they see the original navigation. That dilutes the variation's results.

Seen in
Chrome and Safari at 1152px and 1199px (TC-19, TC-15): combo=2, variation not applied.
Suggested fix
Add a VWO segment condition (custom JS window.innerWidth >= 1200) so these visitors aren't included, or lower the code's breakpoint to wherever the bar layout still fits (the host desktop nav starts at 992px). Resizing after load is handled cleanly (TC-16: below 1200 the original bar comes back, with no duplicate Registration/CTA).

Questions and notes

Question

Q-01 · Goals 1–3 never fire

The experiment defines 16 custom goals. Thirteen fire correctly (see the goal map below). Goals 1, 2 and 3 have no trigger in the page data and never fired during landing, dropdown use, link clicks, the register click or direct visits to any of the 12 pages. If they were meant to be the brief's "Visit FP&A Forum Pricing Page" or a homepage visit, they are duplicates of goal 6 or unwired. Can the team confirm what they are, or delete them?

Note

Q-02 · Wireframe's top bar is older than the live site

The wireframe's control shows an orange "Register for AFP 2026" button and "Join AFP". Live control already has neither: the button is gone and the link reads "Join". So vB.css hiding .cre-t-05-reg and vB.js renaming the link to "JOIN" change nothing today. That's harmless, so nothing needs fixing.

Note

Q-03 · Closed-state underline under PROGRAM in the wireframe

In the wireframe's top variation frame, PROGRAM has the orange underline while no dropdown is open. Live, the underline appears only on the open item, the same as control. This reads as a design hover state; flag it if the intent was a persistent "current section" marker.

Note

Q-04 · Site errors are pre-existing

Both arms log the same page errors ("Invalid or unexpected token", "License expired", HubSpot cross-frame access in Safari). None come from cre-t-43 (TC-17). During the Safari run the origin was briefly down (Cloudflare 522). That run was repeated once the site recovered.
