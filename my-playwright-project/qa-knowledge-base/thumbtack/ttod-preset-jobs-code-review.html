Findings

CR-01 [High] Rule 11: selectors match partial generated class names or generic utility classes

  • JS: [class*="pro-signup-hero_heroSection"], _heroTitle, _heroSubhead, [class*="how-tt-works_section"] (va3.js:5-8) and [class*="pro-signup-hero_searchFields"] button (va3.js:131).
  • CSS: the whole hero block uses [class*="pro-signup-hero_*"] and [class*="TextInput_*"]. It also relies on combinations of generic utility classes that many elements share: .tc.mb5 (va3.css:12, 292), .mw9 (:39), .relative.mv2 (:154, 266).
  • Risk: these are CSS-module names generated at build time. A Thumbtack release that renames the module or component breaks the variation silently. Utility-class combinations can also match the wrong element.
Fix
  • Stable attributes exist for the hero Sign-up buttons: [data-testid="get-started-button-mobile"] and [data-test="get-started-button"]. Another live /pro experiment already uses them. Use these at va3.js:131 instead of the searchFields button + offsetParent lookup. The dev should confirm the desktop attribute is on the hero button.
  • #search-location-input is a stable ID; use it for input styling where possible.
  • Where no stable hook exists (hero section, h1, subhead, How-it-works section), add a comment saying so, so the risk is known.

CR-02 [Medium] Rule 5: no fallback when the Sign-up CTA or hero changes fail

  • Sign-up CTA can do nothing. va3.js:131-137: after scrolling to the hero, the code clicks the first visible hero button. If none is found (selector changed, or the hero fields have moved into the native sticky search bar), the loop ends and nothing happens. The user is scrolled to the top with no signup and no feedback.
  • Changes only hold for 10 seconds. va3.js:146-155: hero copy, bar and section are re-applied only while the 10-second polling loop runs. If React re-renders the hero after that, the h1 goes back to "Find more customers in [City]." and the injected nodes can disappear for good.
  • Low: va3.css:85-87 hides the native <picture> and relies on a CSS background image. If that CDN image fails, the hero shows an empty box.
Suggested fix
scrollToEl(HERO_SECTION, function () {
    // visibleEl(): first match with offsetParent !== null (same check as today)
    var btn = visibleEl('[data-test="get-started-button"], [data-testid="get-started-button-mobile"]');
    if (btn) { btn.click(); return; }
    // Fallback: focus the service field so the user can continue
    var input = document.querySelector(HERO_SECTION + ' input');
    if (input) input.focus();
});

For re-renders after 10 seconds: either extend the poll with a backoff, or use a MutationObserver on the hero parent with a debounce, and disconnect it after N minutes or once the page is stable (rules 6 and 7 then apply).

CR-03 [Medium] Rules 3 / 10: scrollToEl interval has no hard stop and stacks on repeat clicks

  • va3.js:66 starts a new setInterval every time the bar CTA or section CTA is clicked. It stops through its own 3-second logic, but no setTimeout clears it from outside.
  • The handle isn't stored, so a second click doesn't stop the first loop. A double-tap on "See how it works", or clicking the bar and then Sign up, runs two correction loops that fight each other with competing scrollTo calls.
Suggested fix
var scrollCheck, scrollStop;
function scrollToEl(selector, done) {
    clearInterval(scrollCheck);
    clearTimeout(scrollStop);
    ...
    scrollCheck = setInterval(function () { ... }, 150);
    scrollStop = setTimeout(function () { clearInterval(scrollCheck); }, 3500);
}

CR-04 [Low] Rule 8: code that should be removed

  • Duplicate CSS: va3.css:154-160 and va3.css:266-271 set the same pill radius on the same element; the first one also sets a transparent background. Merge them into one rule.
  • Dependency on another experiment: va3.css:154-167 only apply when body.pro-page-updte is present. That class comes from the old experiment 5870164508409856 ("test144"), still running at 100%. When that test is stopped, these rules silently stop working. Scope them to .bm_preset_jobs_pro_lp only.
  • Leftover button styles: .bm-hiw-bar__btn (va3.css:95-108) still has button-reset styles (border:0, margin:0, display:block, width:100%), but it's a <div> now; only the inner .bm-hiw-bar__cta is a button.
  • try/catch catches almost nothing: the one at va3.js:158-166 only wraps the start-up call. Errors inside the interval and click handlers aren't caught, so the debug logging is effectively dead. Move the try/catch inside init and the callbacks, or drop it.
  • Unused ID: id="bm-two-ways" (va3.js:37) isn't referenced anywhere; JS and CSS use the class.

CR-05 [Low] Rule 1: injected-component CSS not scoped to the variation class

The body class bm_preset_jobs_pro_lp is added (va3.js:143) and all hero overrides are scoped to it. The CSS for the injected components (.bm-hiw-bar*, .bm-two-ways*, @keyframes bmArrowFloat) is global. Prefix those rules with .bm_preset_jobs_pro_lp to follow the convention and avoid collisions with other tests.

Q-03 (already raised in QA Round 2): synthetic click can inflate goals

The section CTA calls .click() on the hero Sign-up button. If any goal is tied to clicks on that button, clicks on the new section also count toward it. Confirm with the client whether this attribution is intended, or give the section CTA its own goal.

What passed

  • Rule 2: addBar() and addTwoWaysSection() check for .bm-hiw-bar and .bm-two-ways before inserting (va3.js:99, 105). Adding the body class is safe to repeat.
  • Rule 4: a delegated live() helper, all handlers inside bindEvents(), and a window.bmPresetJobsProLpEvents flag so listeners attach only once (va3.js:110-140).
  • Rule 3 (main loop): the 50ms setup interval is cleared after 10 seconds (va3.js:153-155).
  • Rule 10: the for loop over hero buttons returns as soon as it finds a match.
